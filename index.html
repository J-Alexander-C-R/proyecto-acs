Introducción

Todo software cambia: cambian los requisitos, se corrigen errores, se agregan funciones y se ajusta el diseño. La Administración de la Configuración del Software (ACS), también conocida como SCM, es el conjunto de actividades que permite que esos cambios ocurran de forma ordenada, sin que el equipo pierda el control sobre qué versión es la buena, quién modificó qué y por qué.

En la sección 22.3, Pressman explica que la ACS no es solo "guardar archivos", sino un proceso con tareas bien definidas. Ese proceso no tiene que ser burocrático, pero sí debe dar respuesta clara a preguntas como: ¿cómo identificamos cada pieza del software?, ¿cómo manejamos muchas versiones a la vez?, ¿quién aprueba un cambio? y ¿cómo nos enteramos de lo que cambió?

Objetivos del proceso ACS

Según Pressman, el proceso persigue cuatro objetivos principales:

  1. Identificar todos los ítems que, en conjunto, forman la configuración del software.
  2. Administrar los cambios que se hacen a uno o varios de esos ítems.
  3. Facilitar la construcción de distintas versiones de la aplicación.
  4. Garantizar la calidad del software mientras la configuración evoluciona en el tiempo.

De estos objetivos salen las cinco tareas de la ACS: identificación, control de versión, control de cambio, auditoría de la configuración y reporte de estado. Pressman las dibuja como capas concéntricas: un ítem de configuración (ICS) nace en el centro y, a lo largo de su vida, se mueve hacia afuera atravesando cada capa hasta formar parte de una versión liberada.

1. Identificación de objetos de la configuración

Para poder controlar algo, primero hay que nombrarlo. Cada ítem de configuración del software (ICS) debe tener un nombre único y organizarse con un enfoque orientado a objetos. Pressman distingue dos tipos:

  • Objeto básico: una unidad de información creada durante el análisis, diseño, código o prueba. Ej.: una sección de la especificación de requisitos o el código de un componente.
  • Objeto agregado: una colección de objetos básicos y/u otros agregados. Ej.: la especificación de diseño completa, que agrupa el modelo de datos, el modelo arquitectónico, etc.

Cada objeto se describe con cuatro características:

  • Nombre: cadena que lo identifica sin ambigüedad.
  • Descripción: tipo de ICS, proyecto al que pertenece y datos de cambio/versión.
  • Recursos: lo que el objeto usa o requiere (tipos de datos, funciones, variables).
  • Realización: puntero al contenido real del objeto básico (en un agregado es nulo).

Además, los objetos se relacionan entre sí. La relación <parte de> crea una jerarquía (un diagrama de clases es parte del modelo de requisitos), mientras que <interrelacionado> conecta objetos de ramas distintas de esa jerarquía. Estas relaciones permiten estimar el impacto de un cambio. Por último, el esquema de identificación debe aceptar que los objetos evolucionan: pueden cambiar muchas veces antes y después de convertirse en línea de referencia.

2. Control de versión

El control de versión combina procedimientos y herramientas para manejar las distintas versiones de los objetos de configuración. Un buen sistema de control de versión ofrece:

  1. Repositorio (base de datos del proyecto) donde viven todos los ICS relevantes.
  2. Administración de versiones: guarda todas las versiones de un objeto, o las reconstruye a partir de las diferencias entre ellas.
  3. Facilidad de construcción: reúne los ICS correctos para armar una versión específica del software.
  4. Rastreador de conflictos (errores): registra el estado de los problemas abiertos de cada objeto.

Algunos sistemas trabajan con conjuntos de cambio: un paquete con todos los cambios necesarios para producir una versión, junto con el motivo, el autor y la fecha. Para construir una versión a partir de conjuntos de cambio se usa un modelo del sistema que contiene una plantilla con la jerarquía y el orden de construcción de los componentes, reglas de construcción y reglas de verificación.

Pressman presenta como herramienta típica el CVS (Sistema de Versiones Concurrentes): guarda solo las diferencias entre versiones, da a cada desarrollador su propio directorio de trabajo y mezcla los cambios al final. Sin embargo, CVS no construye versiones ni implementa por sí solo un proceso de control de cambio.

3. Control de cambio

Controlar el cambio es un acto de equilibrio: con muy poco control el proyecto cae en el caos; con demasiado, la burocracia frena el trabajo creativo. En proyectos grandes, el control combina procedimientos humanos con herramientas automatizadas. El flujo general es:

  1. Se recibe una petición de cambio.
  2. El desarrollador la evalúa: mérito técnico, efectos colaterales, impacto y costo.
  3. Se genera un reporte de cambio para la Autoridad de Control de Cambio (ACC).
  4. La ACC decide. Si aprueba, emite una Orden de Cambio de Ingeniería (OCI); si no, se informa al usuario.
  5. Se hace check-out del ICS, se aplica el cambio y se revisa (auditoría).
  6. Se hace check-in, se establece una línea de referencia para pruebas y se aplican actividades de SQA.
  7. El cambio se promueve a la siguiente liberación, se reconstruye y se distribuye la nueva versión.

Dentro de este proceso, el control de versión aporta dos mecanismos clave: el control de acceso (quién puede modificar cada ICS) y el control de sincronización (evitar que dos personas sobrescriban el trabajo del otro).

El nivel de control depende del momento: antes de que un ICS sea línea de referencia el control es informal; cuando ya es línea de referencia se aplica control a nivel de proyecto (aprueba el gerente o la ACC); y cuando el producto se libera al cliente el control es formal. La ACC debe tener una visión global: cómo afecta el cambio al hardware, al desempeño, a la calidad y a la percepción del cliente.

4. Auditoría de la configuración

Identificar, versionar y controlar el cambio pone orden, pero no garantiza que el cambio se hizo bien. Para eso existen dos actividades: la revisión técnica, que verifica la exactitud técnica del ICS modificado, y la auditoría de configuración, que revisa aspectos que la revisión no suele cubrir. La auditoría pregunta:

  1. ¿Se hizo el cambio indicado en la OCI? ¿Se agregó algo más?
  2. ¿Se realizó una revisión técnica?
  3. ¿Se siguió el proceso y los estándares de ingeniería de software?
  4. ¿Se marcó el cambio en el ICS, con fecha y autor?
  5. ¿Se siguieron los procedimientos ACS para anotar, registrar y reportar el cambio?
  6. ¿Se actualizaron los ICS relacionados?

5. Reporte de estado

El reporte de estado de la configuración (REC), o contabilidad de estado, responde cuatro preguntas: ¿qué ocurrió?, ¿quién lo hizo?, ¿cuándo ocurrió? y ¿qué más se verá afectado?

Se genera una entrada REC cada vez que un ICS recibe una identificación nueva o se actualiza, cada vez que la ACC emite una OCI y cada vez que se realiza una auditoría. Esta información puede publicarse en línea para que desarrolladores y gerentes estén siempre al tanto de los cambios importantes.

Ejemplo de una petición de cambio

Supongamos que un usuario reporta que el menú no funciona en el celular. El desarrollador evalúa el impacto (solo afecta styles.css), la ACC —en un equipo pequeño, el líder— aprueba el cambio (OCI), se crea una rama fix-menu-movil (check-out), se corrige, se revisa (auditoría), se integra a main (check-in) y se publica una nueva versión v1.0.1. El git log queda como reporte de estado.

Conclusión

La sección 22.3 muestra que la ACS es un proceso de cinco capas que acompaña a cada ítem de configuración durante toda su vida. Su valor no está en la burocracia, sino en poder responder en cualquier momento qué versión tenemos, qué cambió, quién lo cambió y por qué.
